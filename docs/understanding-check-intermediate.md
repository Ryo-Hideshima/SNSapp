# Webアプリケーション開発 中級編 理解度チェック 提出

## 🔐 第1章: 認証・認可とセキュリティ

### Q1. セッション認証とトークン認証

セッション認証
ログイン情報をサーバー側で覚える。

トークン（JWT）認証
ログインするとサーバーから「認証済みであることを示すトークン」が発行され、
その後はユーザー側が、そのトークンを毎回サーバーに送る。

このアプリでJWTを採用した理由:
・セッション認証の場合、サーバーが増えたときなどに毎回ログインをする必要がでてくるため。
　手間がかかる。
・ReactとSpring Bootを別々に動かす構成では、Cookieでログイン情報を扱うより、
　API通信のたびにAuthorizationヘッダーでJWTを送る方が設計をシンプルにしやすい。

### Q2. アクセストークンとリフレッシュトークン

トークンを2種類に分ける理由:
アクセストークンは毎リクエスト送信するため、万が一漏洩した際の被害を最小化するには有効期限を短くしたい。
しかし有効期限を短くすると頻繁な再ログインが必要になり利便性が落ちる。
そこで「短命で頻繁に使うアクセストークン」と「長命だが失効・ローテーション管理されたリフレッシュトークン」に分離し、
利便性と安全性を両立させている。


### Q3. パスワードのハッシュ化

暗号化、は鍵を使って可逆的にデータを変換する。正しい鍵があれば元のデータに復号できる。
ハッシュ化は、一方向関数で不可逆的にデータを変換する。同じ入力からは同じ出力が得られるが、
出力から入力を逆算することはできない。

パスワード保存にハッシュ化を使う理由:
・パスワードは「元に戻す」必要がないため。
　ログイン時にユーザーが入力した平文パスワードを同じ方法でハッシュ化し、
　DBに保存されているハッシュ値と一致するかどうかだけを確認すればよい。

・万が一DBが漏洩しても、ハッシュ値から元のパスワードを復元できないため被害を抑えられる。

### Q4. 認可（Authorization）

認証は、「あなたは誰か」を確認すること。
認可は、「あなたに何をする権限があるか」を確認すること。

「自分の投稿のみ編集・削除できる」は認可に該当する。

### Q5. CORS設定の実務理解

本番環境でのCORS設定の変更点:
本番環境の実際のドメインに変更

`allowedOrigins("*")`の問題点:
どのサイトからもアクセスできるので、悪意のあるサイトからも侵入されてしまう可能性がある。


### Q6. SQLインジェクション

SQLインジェクションとは: ユーザー入力をそのままSQL文の一部として組み立てることで、
攻撃者が意図しないSQLを注入し実行させてしまう脆弱性。

MyBatisで防ぐための実装上の注意点:
MyBatisには${keyword}という書き方もあるが、この書き方は、悪意のある値が入るとSQLの構造そのものが変わる可能性があるので、
必ず#{}の書き方を使用する。

### Q7. XSS（クロスサイトスクリプティング）

`<script>alert('攻撃')</script>`が投稿された場合そのままHTMLとして他のユーザーのブラウザに描画されると、
投稿者が仕込んだ任意のJavaScriptが閲覧者のブラウザ上で実行されてしまう。

Reactでの対策方法:
`{post.content}`のようにJSX内で変数を展開することで、基本的にはHTMLとしてではなく文字列として扱うことができる。


### Q8. HTTPSと本番セキュリティ

- ALB(Application Load Balancer)を使う場合、SSL/TLS証明書は一般的にALB自体に配置する。

- ALB〜バックエンド間通信のHTTPS必要性: 
ALBとバックエンドが同一VPC内のプライベートネットワークにある場合は必須ではないという考え方もあるが、ゼロトラストの観点や、社内ネットワーク内であっても盗聴・中間者攻撃のリスクを完全には排除できないため、可能であればALB〜バックエンド間もHTTPS化する。
少なくともクライアント〜ALB間は必ずHTTPSにする必要がある。

## 🏗 第2章: アプリケーションアーキテクチャ

### Q9. レイヤードアーキテクチャ

Controller: HTTPリクエストの受け口。リクエストの検証、レスポンスの組み立てのみを担当。
Service: ビジネスロジック本体。「投稿は自分のものだけ削除できる」「フォローは自分自身にはできない」といった業務ルールの判断、トランザクション境界、複数Mapperの組み合わせを担う。
Repository: DBとのやり取りのみ。SQLの実行とオブジェクトへのマッピングに専念する。

なぜ分離するのか:
- 関心の分離により、それぞれのレイヤーを独立してテストできる
- 修正しやすく、バグを減らし、後から機能追加しやすくするため


ControllerとServiceの責務の境界:
- Controllerは「リクエストを受けてServiceを呼び、返ってきた結果をレスポンスとして返す」だけ。分岐やDBアクセスはServiceに任せる。

### Q10. DTOパターン

エンティティを直接APIに使わない理由:
・DBのデータ構造と、APIで外に見せるデータ構造は分けた方が安全で扱いやすいから。（外に出してはいけない
　パスワードまで返す可能性がある）

### Q11. グローバル例外ハンドリング

各Controllerでtry-catchする場合との比較:
グローバル例外ハンドリングを使うことで、各Controllerに同じtry-catchを繰り返し書く必要がなくなり、
エラー処理を一元管理できる。その結果、Controllerが本来のリクエスト処理に集中でき、
エラーレスポンスの形式も統一しやすく、保守性が高まる。

観点	　　　MyBatis	　　　　　　　　　　　　　　　　　　　　　JPA
SQL制御	　　高い。自分でSQLを書く	　　　　　　　　　　　　　低〜中。基本は自動生成
学習コスト	SQL知識が必要だが仕組みは比較的分かりやすい。	　最初は便利だが、内部仕様まで理解すると難しい

### Q13. 環境ごとの設定管理
プロファイルは、「開発環境・テスト環境・本番環境ごとに、使う設定を切り替える仕組み」。

環境ごとに設定を分ける理由
「開発・テスト・本番でDBやCORS、ログなどの設定が違うため、コードを書き換えず、安全に切り替えられるようにするため」

### Q14. Flyway（DBマイグレーション）

マイグレーションツールを使う理由
「データベースの変更履歴をコードとして残し、誰がどの環境で実行しても同じ状態にできるようにするため」
（直接ALTER TABLEしない理由）
直接DBに対して手作業でALTER TABLEすると、環境ごとの変更漏れや実行順序の違い、変更履歴が残らないといった問題が起きやすいため

### Q15. Axiosインターセプター
インターセプターとは: HTTPクライアントライブラリが提供する、リクエスト送信前／レスポンス受信後に共通処理を差し込める仕組み。例えば「全リクエストに認証ヘッダーを自動付与する」「401が返ってきたら自動でトークンをリフレッシュして再試行する」といった横断的関心事を、個々のAPI呼び出しコードに書かずに一箇所で処理できる。

これが無い場合の問題点: すべてのAPI呼び出し箇所で「トークン付与」「401時のリフレッシュ処理」を個別に書く必要があり、コードが大量に重複するうえ、1箇所でも実装を忘れるとそこだけ認証エラーの処理が漏れる（無限に401が返り続けてUXが壊れる、など）。

## 🎨 第3章: フロントエンド設計

### Q16. React Context

なぜpropsではなくContextが選ばれたのか:
Contextを使うと、必要なコンポーネントが直接取得できるため。

適切なケース
認証などの複数の離れたコンポーネントで共通利用する情報のとき。

不適切なケース
「1〜2階層しか渡さないデータ」はpropsの方がシンプルなのでContextは不適切

### Q17. カスタムフック

なぜロジックをコンポーネントではなくフックに分離するのか:
「画面を描くコード」と「処理のコード」を分けて、読みやすく・再利用しやすく・テストしやすくするため


### Q18. コンポーネント設計

良いコンポーネント分割の考え方: 「1つのコンポーネントは1つの責務を持つ」「見た目の単位と再利用性を意識して分ける」。

具体例（このアプリの実装から）:
- `Avatar.tsx`: アバター画像またはイニシャル表示のみを担う、propsだけで完結する純粋な表示コンポーネント。フックも副作用も持たない。
- `PostCard.tsx`: 1件の投稿の表示＋いいね/削除操作を担う。`TimelinePage`・`ProfilePage`の両方から再利用されている。
- `AppHeader.tsx`: ナビゲーション・ログアウトなど画面共通のヘッダー機能を1箇所に集約し、全ページで再利用。
このように「表示のみ」「1件のデータ表示単位」「画面共通UI」という単位で分割することで、変更の影響範囲が局所化され、テストも書きやすくなる（実際`Avatar.test.tsx`・`PostCard.test.tsx`・`AppHeader.test.tsx`をそれぞれ独立してテストできている）。

### Q19. TypeScriptの型安全性

型のメリット:
- API呼び出しの戻り値に型を付けることで、存在しないプロパティへのアクセスやtypoをコンパイル時に検出できる。
　実行時エラーになる前に気づける。
- IDEの補完が効くため開発効率が上がる。

AIコードレビュー時の利点:
- 型定義があることで、AIがコードの意図を正確に把握しやすくなり、AIが提案するコードの整合性チェック（引数の型不一致など）を機械的に検証できる。型エラーという明確な合否基準があるため、AIの生成物のレビュー・修正サイクルが速く回る。

### Q20. SPAルーティング

従来のWebとの違い: 従来型のWebアプリは画面遷移のたびにサーバーへページ全体をリクエストし、サーバーがHTMLを生成して返す（フルページリロード）。
SPA(react-router-dom)はブラウザの`History API`を使い、JavaScriptだけで表示コンポーネントを切り替える（サーバーへの新規ページリクエストは発生しない）。

「直接URLで404になる問題」の原因と対策:
- 原因: SPAのルートに直接アクセス（リロードやブックマークからのアクセス）すると、ブラウザはこのパスをサーバーにリクエストする。サーバー側にこのパスに対応する実ファイルが無いため404になる（SPAのルーティングはあくまでJS側の仕組みであり、サーバーはそれを知らない）。
- 対策: サーバー側で「該当するパスがなければ`index.html`を返す」フォールバック設定を行う。`index.html`が返れば、そこでReact Routerが起動しクライアント側でルーティングを解決する。

### Q21. 楽観的UI更新

- サーバー応答後に更新: ユーザーの操作（例: いいねボタンのクリック）後、APIレスポンスが返ってくるまでUIは変化させず、成功レスポンスを受け取ってから画面を更新する方式。
- 楽観的更新: 「おそらく成功するだろう」という前提で、APIレスポンスを待たずに即座にUIを更新し、後で失敗した場合だけ元に戻す方式。

どちらが適切か: 失敗確率が低く、失敗しても致命的でない操作（いいねのトグルなど）は楽観的更新の方がユーザー体験（体感速度）が良い。一方、投稿の削除や決済など「取り返しのつかない・失敗時の影響が大きい」操作は、サーバー応答後の更新の方が安全。

## ☁️ 第4章: インフラとデプロイ

### Q22. Docker / docker-compose

Dockerの概要: アプリケーションとその実行環境をまとめて「コンテナ」というポータブルな単位にパッケージ化する技術。「自分の環境では動くのに他の人の環境では動かない」問題を解消する。

ローカルインストールとの違い: PostgreSQLを直接ローカルマシンにインストールする場合、OSやバージョンによってセットアップ手順が異なり、複数プロジェクトで異なるバージョンのPostgreSQLが必要な場合に競合する。Dockerであれば一発で、指定バージョンのPostgreSQLをホストを汚さずに起動・破棄でき、チーム全員が同じ環境を再現できる。

### Q23. AWS基本サービス

- EC2: 仮想サーバー。Spring Bootアプリケーション本体を実行する。
- RDS: マネージドなリレーショナルDBサービス。PostgreSQLをAWS側が保守・バックアップ・パッチ適用してくれる。
- ALB (Application Load Balancer): 複数のEC2インスタンスにリクエストを振り分け、SSL/TLS終端やヘルスチェックも担う。
- S3: オブジェクトストレージ。このアプリでは実際にアバター画像の保存先として利用している。

分離理由: 役割ごとに専用のマネージドサービスを使うことで、それぞれ独立してスケール・障害対応できる（例: アプリサーバーだけ台数を増やす、DBだけバックアップ頻度を上げる等）。また画像のような大容量バイナリをDB(RDS)に入れず専用のオブジェクトストレージ(S3)に置くことで、DBの負荷とコストを抑えられる。

### Q24. IaC（Terraform）

手動構築との違いとメリット:
- 手動構築（AWSコンソールをポチポチ操作）は再現性がなく、「誰が何を設定したか」が属人化し、環境間（開発/本番）で構成がずれやすい。
- TerraformのようなIaCはインフラ構成をコードとして記述し、Gitでバージョン管理する。terraform applyで毎回同じ構成を再現でき、変更もコードレビューを経て適用できる。障害時のリソース復旧や、同一構成の複数環境構築も容易になる。

### Q25. 環境変数と機密情報

ソースコードに直接書く問題点:
- Gitリポジトリにパスワードやシークレットキーが平文でコミットされると、リポジトリへのアクセス権を持つ全員（さらにpublicリポジトリなら世界中）に漏洩する。過去のコミット履歴からも復元できてしまうため、後から削除しても手遅れになりやすい。

安全な管理方法:
- 環境変数から読み込む形にし、実際の値はコードに含まれないようにする。ローカル開発では.envファイル（.gitignore対象）やdocker-compose.ymlの環境変数で渡し、本番ではAWS Secrets ManagerやParameter Store、あるいはCI/CDのシークレット機能を使ってデプロイ時に注入するのが望ましい。

### Q26. 構造化ログ

JSONログの利点: 通常のテキストログは人間が読むには適しているが、CloudWatch LogsやDatadogのようなログ集約基盤で検索・集計するには不向き。JSON形式で出力すれば、各フィールド（timestamp, level, message, requestId等）をキーとして機械的にフィルタ・集計できる。

MDCの役割: リクエストごとに`requestId`や`userId`をスレッドローカルな文脈情報として設定しておくと、そのリクエスト処理中に出力される全てのログ行に自動的にその情報が付与される。これにより「あるユーザーの、ある1回のリクエストに関するログだけ」を横断的に追跡でき、障害調査やユーザー問い合わせ対応が格段にやりやすくなる。

## 🧪 第5章: テストと品質保証

### Q27. テストの種類

- 単体テスト: 最も小さい単位（1つの関数・1つのクラス）を、依存先をモックに置き換えて孤立してテストする。
　具体例: `UserServiceTest`（`UserMapper`をMockitoでモックし、`UserService`のロジックだけを検証）、`Avatar.test.tsx`（propsだけで完結する純粋なコンポーネントのテスト）。

- 結合テスト: 複数のコンポーネント・レイヤーを実際に連携させてテストする。
　具体例: `UserMapperTest`（`@MybatisTest`で実際にH2 DBに対してSQLを実行し、マッピングまで検証）、`UserControllerTest`（MockMvc経由でController→Service→Mapper→実DBまで一気通貫で検証）。

- E2Eテスト: 実際にブラウザを操作し、ユーザー視点でアプリ全体の挙動を検証する。
　具体例：
1. ログイン画面を開く
2. メールアドレス・パスワードを入力
3. ログインボタンを押す
4. 投稿一覧画面へ遷移する
5. 新規投稿を作成する
6. 投稿が一覧に表示される
7. ログアウトする
E2Eテストでは、実際のユーザー操作に近い形で、確認する

### Q28. モック（テストダブル）

モックの利点:
- テスト対象を、実際の外部依存（DB、ネットワーク、他クラス）から切り離して高速かつ決定論的に実行できる。
- 「特定の異常系（例: DB接続エラー）」のように、実際に再現するのが難しい状況もモックなら簡単に作り出せる。

注意点:
- モックしすぎると「テストが実装の詳細に依存しすぎて、リファクタリングのたびにテストが壊れる」問題が起きる
- モックの振る舞いが実際の依存先の振る舞いと乖離していると、モックでは通るのに本番では失敗する、という偽陽性を生む。
　結合テストと組み合わせて補完する必要がある。

### Q29. 境界値とエッジケース

「1〜280文字制約」の境界値分析:
- 0文字（空文字）: 制約違反として拒否されるべき（下限の外側）
- 1文字: 許可される最小値（下限の境界）
- 280文字ちょうど: 許可される最大値（上限の境界）
- 281文字: 制約違反として拒否されるべき（上限の外側）

### Q30. テストカバレッジ

カバレッジの意味: テストによってソースコードのどれだけの割合（行・分岐など）が実行されたかを示す指標。

限界:
- カバレッジ100%は「そのコードが1回でも実行された」ことしか保証せず、「あらゆる入力パターンに対して正しい結果を返す」ことは保証しない。
- 境界値やエッジケース（Q29）を網羅していなければ、カバレッジ数値が高くても実際のバグは残りうる。

「100%＝バグなし」は正しくない。カバレッジは「テストされていないコード」を可視化する有用な指標ではあるが、「テストの質」までは測れない。

### Q31. フロントエンドテスト戦略

Testing Libraryの思想:
- 公式の指針は "The more your tests resemble the way your software is used, the more confidence they can give you."（テストが実際の使われ方に近いほど、そのテストは信頼できる）。
- 実装の詳細（内部のstate変数名やコンポーネントの内部構造）ではなく、「ユーザーが画面上で見て・操作できるもの」を基準にDOMを検索・操作する。

利点:
- このアプリの各ページテストは`screen.getByLabelText("メールアドレス")`のようにラベルで入力欄を取得し、`userEvent`で実際のユーザー操作（クリック・入力）をシミュレートしている。これにより、内部実装（stateの持ち方やコンポーネント構造）をリファクタリングしても、見た目・振る舞いが変わらない限りテストは壊れない（＝実装詳細に依存しない、壊れにくいテストになる）。
- アクセシビリティ（`role`や`label`が正しく設定されているか）も自然にテストされる副次効果がある。

## 🧭 第6章: 設計原則と実務判断

### Q32. N+1問題

概念: 一覧を1件取得(1クエリ)した後、各要素に対して関連データを個別に取得するクエリを追加で発行してしまい、結果として「1 + N回」のクエリが発行されてしまう問題。件数が多いほど致命的に遅くなる。

タイムライン例:
例えばタイムラインで20件の投稿を取得した後、投稿ごとに投稿者情報を取得すると、1回＋20回で21回のSQLが発行される。
投稿数が増えるほどDB負荷とレスポンス時間が増える

### Q33. ページネーション

必要な理由: データ件数が増え続けるタイムラインのような一覧を一度に全件返すと、
レスポンスサイズが肥大化しパフォーマンスが悪化する。表示側でも全件を一度に描画するのは非効率。

代表的な2方式:
1.オフセットページネーション: 「何ページ目か」を指定して取得する方式。実装がシンプルで「◯ページ目に飛ぶ」UIが作りやすい。ただしデータが更新され続ける一覧では、ページをめくる間に新しいデータが挿入されると同じ行が重複表示されたりズレたりする問題がある。また`OFFSET`が大きくなるほどDBがスキャンするコストが増える。

2.カーソルページネーション: 一覧の連続性を保ちやすく、新規データの挿入に強い。ただし「N ページ目に直接飛ぶ」ようなUIには向かない。

### Q34. 画像アップロード設計

- DB保存: 実装が単純（追加のインフラ不要）で、初期の開発速度は速い。しかし画像データがそのままDBの行サイズを肥大化させ、DBのバックアップ・レプリケーションのコストが増大する。また画像配信のたびにアプリケーションサーバー・DBを経由するため配信効率が悪い。
- S3保存: DBは軽量なまま保ち、画像本体はS3が担当。CDN（CloudFront等）と組み合わせれば配信も高速化できる。


### Q35. APIバージョニング

代表的な方式:
- URLパスに含める: 最も直感的でわかりやすく、ブラウザで直接叩いても確認できる。破壊的変更をする際に新バージョンのパスを新設し、旧バージョンと共存させられる。
- HTTPヘッダーで指定: URLは変わらず綺麗に保てるが、ヘッダーを見ないと気づきにくく、ブラウザで直接確認しづらい。

特徴の比較: パス方式は運用・デバッグのしやすさで優れ、多くの公開APIで採用されている。ヘッダー方式はリソースのURLという概念を汚さない（同じリソースは同じURLであるべき、というRESTの原則に忠実）が、クライアント側の実装がやや複雑になる。

### Q36. 技術選定

判断基準:
- 要件との適合性: そのプロジェクトが必要とする機能・性能・スケール要件を満たせるか。
- チームの習熟度・学習コスト: メンバーが既に知っているか、学習に要する時間は許容範囲か。
- エコシステム・実績: ドキュメントの充実度、コミュニティの活発さ、長期的なメンテナンス継続の見込み。
- 運用コスト: ホスティング費用、スケーリングのしやすさ、監視・デバッグのしやすさ。

React + Spring Boot + PostgreSQL の場合の具体化:

- React: SPAとしてリッチなUI（無限スクロール、楽観的な状態更新等）を実現しやすく、コンポーネント単位での再利用・テストがしやすい。エコシステムが非常に大きく、学習リソースも豊富。

- Spring Boot: Java/Kotlinエコシステムの成熟したフレームワークで、DI・セキュリティ（Spring Security）・バリデーション・DBマイグレーション（Flyway）連携などがエコシステムとして揃っており、「認証」「認可」「例外ハンドリング」のような中級レベルの関心事を標準的な作法で実装できる（本アプリもこの恩恵を強く受けている）。

- PostgreSQL: OSSで実績が豊富なRDB。`ON CONFLICT DO NOTHING`のような便利な拡張構文、UNIQUE制約・CHECK制約による整合性担保など、本アプリのようにデータ整合性を重視するSNS系アプリと相性がよい。
